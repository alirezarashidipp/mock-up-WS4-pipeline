# Incident-to-engagement linking

Run `python -m app.linking.pipeline` from the project root, after [classification review](dashboard_app.md).

```text
LLM_OUTPUT.csv + CLASSIFICATION_REVIEW.csv + ENG_ALL.csv
    -> require current human approval -> find supplier candidates -> ask LLM -> save INC_LINKED.csv
```

## Human approval gate

Load original model results and their saved classification reviews together. A Supplier incident enters candidate search only when `classification_review_status` and `supplier_review_status` are `approved` or `corrected`, the reviewed class is SUPPLIER, and the reviewed supplier name is usable. Search with `reviewed_supplier_name`, not a rejected model name. A human can resolve an original UNCERTAIN or failed model result without rewriting it.

Approved/corrected HSBC rows are saved with `link_status=NOT_APPLICABLE` and no candidate search or model call. Pending, Needs review, incomplete supplier decisions, and reviews that no longer match the source row are excluded from the output until resolved. Dashboard approval prepares the next CLI run; it does not automatically call the provider.

Preserve the original classification, processing status, supplier details, and evidence score alongside the six review fields. Send those fields as context, with the human-approved class/name taking precedence over conflicting model proposals. Human approval establishes the attribution used for matching, not a confirmed engagement link.

Before requesting a row again, compare its source and review fields with any existing output. An identical saved row is skipped unless its `link_status` is FAILED. A saved FAILED row stops the rerun and requires a fresh output file to retry; it is not automatically requested again. Changed source values or review decisions for an already-saved ID require a fresh output batch rather than an additional paid request or an overwrite of its earlier result. New approvals can append on a later run. A changed output schema also requires a fresh batch.

INC_LINKED.csv and HUMAN_REVIEW.csv are saved snapshots. Editing an earlier classification review does not rewrite existing linking results or invalidate decisions inside the later file automatically. The next linking run detects changed source/review fields for a saved ID and stops. Preserve the previous snapshots, use a fresh linking output, and prepare a fresh post-link review file for the new results.

## Candidate limit

Set the maximum candidates per incident in the project `.env`:

```dotenv
LINK_MAX_CANDIDATES=70
```

The pipeline loads this setting before candidate search. It must be a positive integer and defaults to 70 when omitted. Keep the first matching rows in ENG_ALL.csv order and stop when the limit is reached. This is a row-count cap, not a relevance ranking or token limit; a relevant engagement later in the file can be excluded.

Python records `link_candidate_count` immediately after candidate search and includes it when saving the INC_LINKED.csv row:

- A positive integer counts the shortlisted ENG_ALL rows prepared for the LLM request, after the cap. Synthetic example: 30 Google candidates gives 30; 100 matching rows with a cap of 70 gives 70, not 100.
- `0` means the approved, usable supplier name produced no candidates; no linking request follows. Blank or Unknown names cannot complete the current human approval gate and therefore do not produce new output rows. Older files may have used zero for those cases.
- A blank cell means candidate search did not run, such as an approved HSBC row. Unresolved reviews are held out of new output entirely; legacy skipped rows may also have a blank count.

The count is not generated by the model. It remains recorded if the request or response later fails, so a positive count alone does not prove the provider received the request. A row matching both name columns is counted once. Historical files without this column have an unknown count; do not fill them with zero. The engagement and human-review detail dropdowns show this saved field automatically.

## Request defaults

Linking uses provider defaults for temperature and output length, with no local token-counting step or tokenizer download. Requests preserve the complete shortlisted rows; the provider's model limits still apply. `LINK_MAX_CANDIDATES` remains a row-count cap, not a token budget. Incomplete or invalid output still fails validation. See [request defaults](llm.md#request-defaults).

## Per incident

1. Keep the complete LLM_OUTPUT row, including `evidence_column` and `attribution_evidence_strength`, plus its six saved classification-review fields. Apply the human approval gate above before searching or requesting a link.
2. For each ENG_ALL row, compare `reviewed_supplier_name` with `THIRD_PARTY_NAME` first; check `THIRD_PARTY_NORMALISED_NAME` only if the first name does not match. Add the row once if either matches, then move to the next row until the candidate limit is reached. Apply the same normalization to supplier and candidate names: Unicode NFKD, ASCII folding (remaining non-ASCII characters are dropped), lowercase, then join ASCII letter/number tokens with single spaces. Extra spaces and punctuation are removed as separators; words remain separated. Synthetic name example: `Google UK` becomes `google uk`, not `googleuk`. Match by whole-word containment or fuzzy similarity at 0.8. Name similarity retrieves candidates, not a confirmed link. Blank/Unknown names produce no candidates. Lexical matching can miss aliases such as EY versus Ernst & Young.
3. Send the incident fields, prior model results, saved human decisions, all shortlisted candidate rows, and `prompts/linking.yml` together in one LLM request per eligible incident. Candidate rows keep their original values; normalization is only for matching. Keep INCIDENT_ID local. Prior model results are context, not proof. Reuse `app/llm/llm_connection.py` and its OpenAI/Azure settings.
4. The model chooses one candidate ENGAGEMENT_ID or null when evidence is insufficient or ambiguous. Return a short reason, `link_confidence` as an integer from 0 to 4 using the link evidence rubric below, and separate incident/engagement source-column name lists, without quotes. This score concerns the engagement match; it is separate from classification's attribution evidence strength. Strong Supplier attribution does not by itself establish an engagement match.
5. Validate the response structure and selected ID against exactly one candidate. Evidence fields must be lists of strings; both lists must be nonempty for a selected engagement. Source names are not checked against input headers, deduplicated, or corrected. Reject noninteger scores, values outside 0-4, a selected engagement with score 0, and a null selection with score 3 or 4. Do not repair the selection or score. Copy the selected engagement's actual CSV values; do not generate its details with the model.
6. Save that row before processing the next incident. Never modify LLM_OUTPUT.csv, CLASSIFICATION_REVIEW.csv, or ENG_ALL.csv.

## Remaining output checks

| Check | Current behavior |
| --- | --- |
| Completion | Require a choice, `finish_reason=stop`, nonempty content, and no refusal. |
| JSON schema | Require the five defined fields and their types; reject extra JSON fields. |
| Reason | Require a string that is not empty or whitespace-only. |
| Evidence strength | Require a strict integer 0-4; selected links allow 1-4 and null selections allow 0-2. |
| Selected engagement | Require null or an ID matching exactly one supplied candidate; a selected ID cannot be blank. |
| Evidence lists | Require lists of strings; both lists must be nonempty when an engagement is selected. |
| Evidence names | No Python check of source membership, spelling, duplicates, or blank individual strings. |

The five JSON field names remain part of the response schema. The removed checks concern source names inside the two evidence lists. CSV schema and conflicting-ID checks remain separate.

## Link evidence strength

The field name remains `link_confidence`, but new responses measure recorded evidence for a unique engagement link, not probability or measured accuracy.

| Score | Display label | Recorded support for the link |
| --- | --- | --- |
| 0 | Unsupported | No recorded evidence supports a unique engagement; return null. |
| 1 | Weak | Only indirect references or a general fit support a candidate. |
| 2 | Moderate | Relevant service or context matches, but material gaps or ambiguity remain. |
| 3 | Strong | Concrete incident and engagement facts distinguish the selected candidate. |
| 4 | Very strong | An explicit documented connection has consistent supporting details and no unresolved material contradiction among the supplied candidates. |

A selected engagement allows scores 1-4; a null selection allows 0-2. For a null selection, the score describes available evidence for linking, not confidence in abstaining. A score of 4 is not 100% accuracy. Return the integer only; the dashboard derives its label. Pydantic requires an integer and rejects strings, booleans, and floats. When no linking LLM call occurs, leave the score blank rather than inventing a score.

## Output

- Preserve every original LLM_OUTPUT column and the six classification-review fields. Add every ENG_ALL column with an `ENG_` prefix; for example, `ENG_ENGAGEMENT_ID` and `ENG_THIRD_PARTY_NAME`. Leave these cells empty when no engagement is selected.
- The LLM returns five fields: `linked_engagement_id`, `link_reason`, `link_confidence`, `link_incident_columns`, and `link_engagement_columns`.
- Python adds `link_status`, `link_error`, `link_candidate_count`, and `link_confidence_scale`. New rows use `link_confidence_scale=0-4`, including rows with a blank score. The scale marker is not generated by the LLM.
- Join source-column lists with comma and space in their respective cells. Store no JSON, prompt, or evidence quotes.

| link_status | Meaning |
| --- | --- |
| MATCHED | The model selected one supplied engagement. |
| UNDECIDED | No candidates for the approved supplier name, or insufficient evidence to select one. Legacy rows may also describe an unknown supplier. |
| NOT_APPLICABLE | Human-approved classification is HSBC; no linking request. |
| SKIPPED | An ineligible direct call or a preserved legacy skipped row; the current batch pipeline holds unresolved reviews out of the output. |
| FAILED | The linking request or response failed validation. |

Provider/invalid-response failures are saved where possible, then stop the batch; earlier rows remain saved. The shared writer retains schema and conflicting-ID checks. Use a separate output file for changed decisions rather than overwriting saved results.

Old INC_LINKED.csv files without `link_confidence_scale` retain their original 0-100 confidence values. Never convert them or infer the scale from the number: an old value of 3 is not a new 3/4 evidence score. The dashboard labels these values as legacy confidence. The six classification-review fields, scale marker, and `link_candidate_count` are part of the new CSV schema, so an existing nonempty file missing these fields cannot accept new rows. Use a fresh output file or batch folder, update `OUTPUT_FILE` in `app/linking/pipeline.py` and `RESULTS_FILE` in `app/ui/engagement_dashboard.py`, and preserve older files. If preparing human review for the new batch, configure its input and a fresh HUMAN_REVIEW.csv output in `app/human_review/pipeline.py`, then point the review dashboard at that output. Existing reviews cannot be reused across a changed source schema.

The classification dashboard preserves LLM_OUTPUT.csv and saves its human decisions separately in CLASSIFICATION_REVIEW.csv. The separate [engagement dashboard](engagement_dashboard.md) reads INC_LINKED.csv and groups linked incidents under engagements. Candidate retrieval is a simple lexical demo and does not guarantee all relevant engagements are found. Offline simulated checks do not establish live matching accuracy.
