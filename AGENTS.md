## Python pipeline

- Keep `app/data_preparation/pipeline.py` linear: read, rename, clean, save CLEAN.csv. Keep `app/llm/pipeline.py` separate: read CLEAN.csv, load definitions, classify, save LLM_OUTPUT.csv.
- Names belong in `fields/columns.yaml`; definitions keyed by standardized names belong in `fields/definitions.yml`; instructions belong in `prompts/classification.yml`.
- Use Pydantic for model inputs and responses. Exclude INCIDENT_ID from model input.
- Cleaning removes invisible control/format characters only; preserve punctuation, emails, HTML, and normal whitespace. Preparation retains empty/repeated IDs and uppercases unmapped headers; add no ID, CSV-shape, or mapping-collision checks to that stage.
- Model classification is HSBC, SUPPLIER, or UNCERTAIN. Use UNCERTAIN when the evidence cannot support choosing the accountable party; this is a successful result, not a processing failure. Explain missing or conflicting facts in decision_rationale. Supplier details are null for HSBC and UNCERTAIN; for SUPPLIER extract only documented facts and use Unknown for missing core details. Keep additional nonduplicated supplier facts in supplier_more_info, or null when none exist.
- Score attribution_evidence_strength from 0 to 4 using the prompt rubric. For UNCERTAIN use 0-2 to describe support for attributing a party, not confidence in uncertainty. Reject an UNCERTAIN response with a score above 2 and an HSBC/SUPPLIER response with score 0. HSBC/SUPPLIER scores 1-4 remain valid. Reject inconsistent responses without changing their classification or score. The score is evidence strength, not a probability.
- Order model inputs as narrative, causes, closure/resolution, investigation history, supplier/product context, then remaining metadata. Preserve every non-ID field and value. Order response fields as root cause, supporting evidence, rationale, classification, evidence strength, then the six supplier fields.
- Save each result in `app/llm/save_csv.py` before requesting the next row. The model's evidence_column is a list of strings; an empty list is accepted and there is no fixed maximum count. Save an empty list as a blank evidence_column cell without failing classification. The prompt requests relevant source names, but Python does not validate source-name membership, spelling, uniqueness, or blank individual strings. Preserve the returned entries without trimming, correcting, or deduplicating them. A referenced source value may be empty to identify missing information. Preserve the returned name order and join names with comma and space in exactly one evidence_column CSV cell, such as COLUMN_X, COLUMN_Y. New outputs have no supporting_evidence or numbered evidence columns. Keep source values and scalar model fields in their own columns, without evidence quotes, JSON blobs, definitions, or prompt text.
- Existing output does not block starting the LLM pipeline; preserve records and retain conflicting-ID checks when saving.
- Use provider defaults for temperature and output length in classification and linking. Do not send `temperature`, `max_tokens`, or `max_completion_tokens`, and do not perform local token counting or download tokenizer data. Preserve complete inputs, structured response validation, and incomplete-response checks. Keep the independent `LINK_MAX_CANDIDATES` cap.
- For classification Pydantic failures, record only recognized response field names and error types in the error cell and console; never include source values, raw model responses, arbitrary extra keys, or credentials. Preserve the existing save-and-stop behavior.
- Preserve response-structure checks and safe CSV writing. Store returned supporting source names as text. Avoid custom exception layers.
- Keep engagement linking independent in `app/linking/`: preserve LLM_OUTPUT rows, select only a supplied ENG_ALL candidate or leave the link undecided, and save INC_LINKED.csv. Only successful SUPPLIER classifications enter matching. UNCERTAIN is SKIPPED without candidate search or an LLM call and does not stop the batch. Load the positive integer LINK_MAX_CANDIDATES from .env before candidate search, defaulting to 70. Keep the first matching rows in ENG_ALL order up to that limit; check THIRD_PARTY_NAME before THIRD_PARTY_NORMALISED_NAME within each row and add it once. Normalize names only for matching, preserve source values, and do not imply relevance ranking. Reuse the existing LLM connection; keep the classification dashboard on LLM_OUTPUT.csv.
- Python records `link_candidate_count` immediately after candidate search and includes it when saving INC_LINKED.csv: the shortlisted ENG_ALL row count after LINK_MAX_CANDIDATES, zero for no candidates, and blank when search is skipped. Retain the count if the request or response fails; it describes prepared candidates, not proof of delivery. Keep the five-field LLM response unchanged. Preserve older files without the column and use fresh linking and human-review outputs for the changed schema; do not invent historical counts.
- Do not validate the names in `link_incident_columns` or `link_engagement_columns` against input headers. Preserve returned strings and order. Keep list-type checks and require both lists to be nonempty for a selected engagement.
- Keep `link_confidence` as a strict integer 0-4 describing engagement-link evidence, not probability: unsupported, weak, moderate, strong, or very strong. A selected engagement allows 1-4; a null selection allows 0-2. Reject inconsistent responses without changing the ID or score. Leave the score blank when no linking call occurs. Python adds `link_confidence_scale=0-4` to new INC_LINKED rows; the LLM still returns five linking fields. Preserve markerless legacy 0-100 results and use a fresh output file for the new schema.
